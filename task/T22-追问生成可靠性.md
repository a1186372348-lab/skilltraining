# T22 追问生成可靠性（生成中/失败分离 + 空内容重试 + 追问预算上调）

状态：IN_PROGRESS（2026-10-07 立项，产品负责人决策"先进行生成中/失败分离，并深度调查失败原因"）

## 背景与根因（2026-10-07 主代理实证调查）

咖啡题会话（3811f356）首答后页面显示「总监暂时离开（追问生成失败）」。证据链：

- 服务端日志：`training.followup_generation_failed`，错误「MiMo API 响应缺少 choices[0].message.content」；该次调用 `status:200, attempts:1, latencyMs:59980`；first-answer 端点总耗时 61s。
- 同日评分调用：`status:null, attempts:4, latencyMs:243574, error:timeout`，随后重试成功（232s）；证明当日 MiMo 服务端处于高负载/退化状态。
- 复现验证（scripts/regen-followup.ts）：**同一输入、同一 2048 预算**，约 1.5 小时后重试成功（18s，completion 仅 623 tokens）——失败是瞬时的，非输入必然触发。
- 根因结论（三层）：
  1. **触发面**：MiMo（推理模型）高负载下推理 token 暴涨，计入 max_completion_tokens 后正文被截空（`server/ai/followup.ts` 注释记载的已知模式，800 实测截空 → 本次 2048 空响应）；
  2. **客户端加重**：`server/ai/mimo-client.ts` 把「200 但 content 为空」归类为不可重试结构错误（catch 中 MimoApiError 一律 break），单次失败即放弃——当时若重试大概率自愈；
  3. **产品层**：追问失败无恢复通道（首答幂等不重新生成），且「生成中」与「已失败」共用同一兜底文案，用户无法分辨。

## 目标

1. 前端能区分「追问生成中」与「追问生成失败」，生成中自动等待，失败才显示兜底；
2. 「200 空 content」纳入指数退避重试，瞬时退化自愈；
3. 追问生成预算 2048 → 4096，给重负载推理留余量（注释授权的既定维护动作）。

## 范围外

- 评分（scoring）链路的预算/超时调整（当时已被重试+轮询兜住，先观察）；
- 追问失败后的「重新生成追问」用户入口（待产品负责人看过本批效果后再议；运维补救可用 scripts/regen-followup.ts）；
- MiMo 供应商切换评估。

## 受影响模块/数据/接口

- `server/ai/mimo-client.ts`：空 content 错误标记 retryable；catch 分支对 retryable 的 MimoApiError 也走退避重试；
- `server/ai/followup.ts`：maxCompletionTokens 2048→4096（注释同步更新实测记录）；
- `server/modules/training/today-view.ts` + `app/today/contract.ts`：TodayView 增加 `firstSubmittedAt: string | null`（ISO）下发；
- `app/today/view-model.ts`：新增纯函数 `followupEmptyState(firstSubmittedAt, now): "generating" | "failed"`（生成窗口 120 秒）；
- `app/today/training-flow.tsx`：追问阶段 followups 为空时按状态渲染——generating 显示「总监思考中…」并每 5 秒重拉（followups 到达或超阈值自动转 failed）；failed 保持现有兜底文案并补一句「若追问稍后生成成功，刷新页面即可看到」；提交首答的响应若 followups 为空（服务端重试已耗尽）直接置 failed，不再等窗口；
- 无 schema 变更、无迁移。

- 回滚点：上述 5 个文件；数据零改动。
