# 能力模型定义 v0.2（评分基准）

> 文档类型：计划方案（docs/ 区）；V2 题库评审与评分调优的统一"尺子"
> 来源：产品方案 v0.3 §6（八维名称）+ 2026-10-08 产品负责人逐维审定的定义与边界（本文档以其为准）+ BR-6（同分不同病）
> 状态：产品负责人审定版；T27/T28/T33 评审与评测集建设均以此为准

## 0. 总则

八个维度覆盖一次产品判断的主要任务：理解情境、界定问题、解释原因、判断价值、设计行动、配置资源、验证判断、沟通决策。

- **八维按主要判断任务区分，允许相互关联。** 用户理解、根因分析、指标与验证可以在判断过程中反复进行，产品表达贯穿各环节；下方的排列顺序适合作为学习导航，不规定为每次判断必须依次走完的固定流程。
- 每道题主测 1 维、辅测 1~3 维；主测维度看「产出质量」，辅测维度看「支撑质量」。
- 维度分 = 该维度历史有效分简单平均（BR-6）；同一分数必须能区分不同病因（如「独立但浅」与「深但依赖提示」），评分诊断须落到具体表现而非只给分。

## 八维定义总表

| 维度 | 定义 | 主要回答的问题 |
|---|---|---|
| 用户理解 | 理解相关用户在具体场景下的目标、行为动机、约束与差异。 | 谁在什么处境下，希望完成什么，为什么这样行动？ |
| 问题定义 | 将模糊诉求界定为有明确对象、场景、目标差距与处理边界的问题。 | 本次究竟要解决什么问题？ |
| 根因分析 | 分析问题发生的关键原因，形成并比较有依据、可检验的因果解释。 | 问题为什么发生，哪些解释更可能成立？ |
| 产品价值判断 | 判断解决某个问题或投入某个方向，能否创造足以支持投入的用户与业务价值，以及价值成立的条件。 | 为什么值得做，价值对谁成立？ |
| 方案设计 | 在现实约束下，设计能够作用于关键问题的机制、流程与交互，并处理关键异常。 | 具体通过什么方式解决问题？ |
| 产品取舍 | 在目标与资源约束下，比较备选做法的收益、代价与风险，确定投入、范围和优先级。 | 选择什么、放弃什么，做到什么程度？ |
| 指标与验证 | 设计验证方法，用合适的指标与证据检验关键判断和方案效果，并据此更新决策。 | 如何知道判断是否成立、方案是否有效？ |
| 产品表达 | 面向特定听众，清楚、准确地传递产品判断及依据，并理解和回应关键异议。 | 如何让对方理解判断，并据此作出决策？ |

## 1. 用户理解

**测什么**：
- 给出有依据的用户分层（核心用户与增量、不同处境下的差异，不是「所有年轻人」）；
- 还原具体使用场景链（何时何地、带着什么约束、一步步怎么用）；
- 解释行为背后的动机与心理机制（为什么一边吐槽一边复购），而非贴标签（「因为便宜」「因为懒」）；
- 能识别多方角色（用户/供给方/平台）各自的目标、约束与张力。

**边界**：用户理解提供有关「人」的认识；问题定义据此界定本次要改变的「状态」。它是素材与证据，不是问题结论。

**典型强/弱**：强——「月底见底的学生、午休紧张的白领，同一单 12 元解决的是不同问题」；弱——画像只有人口属性没有场景与动机、把用户当均值人。

## 2. 问题定义

**测什么**：
- 把模糊诉求界定为结构清楚的问题：**有明确对象、场景、目标差距与处理边界**——当前发生什么，希望达到什么，两者差在哪，本次处理到哪里；
- 区分「诉求的复述」与「待验证的问题定义」：如「店员需要更准确的识别」是诉求，「识别结果中的错误让店员反复核查，无法节省整理时间」才是问题定义；
- 不追求「深刻答案」，追求「清楚、可验证」——好的定义能直接导出验证动作与方案方向。

**边界**：与「用户理解」——用户理解产出对人的认识，问题定义产出对本次要改变状态的界定；与「根因分析」——问题定义回答「本次要解决什么」，根因分析回答「它为什么发生」。

**典型强/弱**：强——说清当前状态、期望状态、差距与本次处理边界；弱——把题面诉求复述一遍、定义大而无当无法导出任何动作、为了显得深刻而追求「真正的问题」。

## 3. 根因分析

**测什么**：
- 形成**有依据、可检验**的因果解释（机制、激励、结构如何导致现象），每一环有事实支撑；
- **形成并比较多个解释**：外部环境、用户行为、内部机制都可能成为关键原因——能说明「现有证据支持 A，但还无法排除 B」是成熟的根因分析；
- 明确指出证据的边界：哪些解释目前无法区分、还需要什么证据；
- 对「官方解释」保持检验意识（承认合理部分，也追问被解释掉的部分）。

**边界**：根因分析负责**提出和比较解释**；指标与验证负责**设计如何检验这些解释**。不要求每次找到唯一、最深层的根因——在证据不足时强行收敛到单一根因是扣分项而非加分项。

**典型强/弱**：强——「现有证据支持买量增长机制，但还无法排除自然增长见顶，需要 X 数据区分」；弱——把第一个看到的解释当根因、为了显得深而强行追唯一根源、因果链中间断环靠想象补。

## 4. 产品价值判断

**测什么**：
- 判断**价值来自哪里、对谁成立**（用户价值/业务价值/多方价值），以及价值**成立的条件**；
- 立场明确且判据具体可检验，而非「既公益又赚名声」两头好话或「做成了所以值得」倒推；
- 能处理「不直接变现」的价值（间接/战略价值框架），而非只用收入利润衡量；
- 给出可迁移的判断标准并能应用到新情境。

**边界**：与「产品取舍」按**判断重点**区分——价值判断回答「价值是否成立、是否足以支持投入」（如「人工纠错能否明显减少店员工作量」）；产品取舍回答「在现实约束下采取哪种行动、分配多少资源」（如「提高识别准确率、建设纠错能力、完善商品库，当前先投入哪个」）。决定继续、收缩或停止本身就含取舍，不按「单选项 vs 多选项」机械划分。

**典型强/弱**：强——「值得，但成立条件是 X；若 X 消失结论反转」；弱——立场骑墙、判据不可检验、只看需求存在不看解决成本。

## 5. 方案设计

**测什么**：
- 设计**作用于关键问题的具体机制**（规则、流程、激励怎么改），以及**用户和相关方如何在其中行动**；
- 覆盖相关各方（用户/供给/平台），说明利益与压力如何重新分配；
- 处理关键异常：异常场景（恶劣天气、出餐慢、交付难小区）从常态规则拆出单独设计；
- 给出可落地节奏（先后次序、试点推广、配套措施），技术与成本基本可行。

**边界**：方案设计限定为「**在这个范围内如何运作**」——判断框架、指标体系、汇报结构不称作方案（分别归指标与验证、产品表达）。**操作流程的先后属于方案设计；资源投入的先后属于产品取舍**——取舍决定范围与投入，方案设计说明范围内的运作。

**典型强/弱**：强——把「配送时间」拆成「如何生成/如何展示/如何考核」三个环节分别设计；弱——方案只有方向没有机制（「优化算法」「加强运营」）、只解决一方把压力转嫁给另一方。

## 6. 产品取舍

**测什么**：
- 在目标与资源约束下比较备选做法的**收益、代价与风险**，确定**投入、范围和优先级**；
- 明确立场与排序，并对次要方向给出具体处理（收缩/限定预算/退出止损），不含糊其辞；
- 识别机会成本（同样的资源投到别处的替代收益）；
- 看到代价在不同相关方之间如何分配（谁受益、谁买单）。

**边界**：与「产品价值判断」——两者都会考虑收益和成本，但主要任务不同：价值判断评估价值成立性，取舍决断行动与资源配置；与「方案设计」——取舍定「做什么、放弃什么、做到什么程度」，方案设计定「在定下的范围内如何运作」。

**典型强/弱**：强——「继续做 A 但收缩到核心 20 城，用 X 信号验证；B 限定预算观察」；弱——全都要、只算收益账不算代价账、排序没有依据。

## 7. 指标与验证

**测什么**：
- **贯穿整个判断过程**：可以检验用户假设、问题定义、根因解释、价值判断，也可以验证方案效果——不止「判断方案是否有效」；
- 先把「好不好」翻译为可证伪的命题，再选指标；指标分层（结果/过程/护栏），避免只盯单一结果；
- 识别虚荣指标（低基数高增速、激励推高的活跃、同源污染的互相印证）；
- 给出判断基准（比什么、什么算成立、什么算证伪）与对比式验证设计（前后/分组/自然实验）；
- **知道证据能说明什么，以及它的限制**——「某项证据还不足以下结论」是验证允许得出的合法结果，且是严谨性的体现。

**边界**：根因分析提出解释，指标与验证设计如何检验解释；别的维度产出判断，这个维度产出「如何知道判断对不对」以及「现有证据能支撑到什么程度」。

**典型强/弱**：强——「看补贴退坡后的自然留存，区分买来的活跃与长出来的活跃；若数据拿不到，则说明当前证据不足以定论」；弱——堆砌指标没有判断基准、被官方战报口径带着走、把没有证据的判断包装成结论。

## 8. 产品表达

**测什么**：
- 观点明确且前置（结论先行，不让听众自己找观点）；
- 依据关系清楚（每个理由落到具体事实，而非抽象口号）；
- 按听众的认知与情绪切入（向上汇报 ≠ 向同事解释 ≠ 向用户公告），控制信息密度；
- **理解和准确回应关键异议**——先听懂对方反对什么，再回应到点上；结尾给出支持决策的下一步。

**边界**：表达评价的是**信息如何被传递**，不是判断内容本身是否成立（内容由相应维度负责）。**表达的目标是让听众准确理解判断及依据、支持其作出决策**——「有说服力」是优秀表现，但「对方接受结论」不是目标：对方理解了依据和代价后，仍可能合理地反对，这不构成表达失败。

**典型强/弱**：强——「开头一句结论、三条落到事实的依据、准确复述并回应最强反对、结尾一个行动建议」；弱——铺垫半天没观点、堆砌信息不考虑听众、回避或曲解异议。

## 9. 对评分与出题的应用约定

- **主测维度评分**：对照该维度「测什么」逐条给证据，Rubric 条目即从这些判断点衍生；
- **辅测维度评分**：只看其作为主测的支撑表现（如主测方案设计的题里，用户理解只看「方案是否建立在对用户的准确理解上」），不按完整标准求全；
- **四条反机械化规则**（源自维度定义与 2026-10-08 题库评审共识，评分 prompt 须体现）：
  1. 根因分析与指标验证：不得因「未给出唯一确定结论」扣分——有依据地比较多个解释、明示证据边界的作答应得高分；但**「承认未知」不自动获得高分**：须先充分利用已有信息，再说明具体缺口及什么证据会改变判断（评审共识 3）；
  2. 指标与验证：「现有证据不足以下结论」+ 说明需要什么证据，是合法且严谨的产出，不得按「没有给出结论」扣分；
  3. 产品表达：不得因「听众最终未接受结论」扣分；评价对象是传递质量（明确、清楚、回应异议），不是说服结果；
  4. 材料中的官方解释与作者观点可作为分析对象：评分看用户如何使用和检验它们，而非是否复述或盲从（评审共识 2）。
- **题目输入与提示的边界**：案例背景与五份阅读资料属于题目输入，阅读不算使用提示、不降低独立完成系数（与 BR-3 一致）；题包通过评审前，须核对完整资料与答案样本是否遵守本节评分规则（评审共识 4）。
- **「同分不同病」诊断**（BR-6）：评分诊断文本必须写明丢分落在哪个判断点上（如「能分层但场景链断裂」），这是反馈页「最需要优化的一个问题」的素材；
- **出题对照**：每道题的 Rubric 条目须能回指到本文件对应维度的判断点，评审时逐条核对（T33 各批评审动作之一）。
